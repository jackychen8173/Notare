## 2026-09-10 (3)

- Built the Sage Chat feature end to end (9-task plan, `sage-chat` branch): a tool-use conversational interface letting a tutor ask Sage to look things up or take actions on their behalf, on top of the existing one-shot Sage endpoints (`draft-notes`, `review-submission`, etc.) which stay untouched.
  - **Data model** (`V13__create_sage_chat.sql`): `sage_conversations` (tutor-owned, one row per conversation) and `sage_messages` (role `USER`/`ASSISTANT`/`TOOL`, ordered, a `content` jsonb column holding a list of `StoredBlock` variants — text, tool-use, tool-result — so a single message can carry Sage's prose plus the tool call it made in one turn). `PendingAction` is a fourth, denormalized jsonb column on the message row (`toolName`, `toolUseId`, `input`, `description`, `actionStatus`) rather than a separate table, since a message has at most one pending action and it's read/written atomically with the message itself.
  - **Tool set** (`SageToolDefinitions`/`SageToolExecutor`, tutor-scoped, same 404-not-403 ownership pattern as every other tutor-facing endpoint): six read categories — students, courses, assignments, submissions (including rubric scores, though `list_submissions`/`get_submission` return an empty rubric-scores list rather than the real ones as a deliberate, flagged simplification), sessions, and AI-generated student-progress summaries — plus four write actions — `release_feedback`, `schedule_session`, `complete_session`, `post_announcement`.
  - **Tool-use loop and confirm/decline** (`SageChatService`): read tools execute immediately and feed their result back to the model in the same turn; a write tool call instead stops the loop and surfaces a `PendingAction` in `PENDING` status for the tutor to approve or reject through the UI — the model never executes a write itself. Confirming re-enters the loop and actually runs the tool (turning it into `CONFIRMED`); declining short-circuits it (`DECLINED`) and tells the model the user declined, without calling the tool executor at all. Only the first `tool_use` block in a turn is acted on when the model requests several AND at least one of them is a write call, since pausing the loop for tutor confirmation would strand any sibling tool_use blocks unresolved; when a turn's tool_use blocks are all read calls, every one of them is executed together in that same turn. Anthropic API failures map to a 502; a write tool erroring during execution is caught and returned to the model as an `is_error` tool result rather than crashing the request.
  - **REST API** (`SageChatController`, all under `/api/sage/chat`, tutor-scoped from the JWT): `GET /` (list conversation summaries), `GET /{id}` (full message history), `POST /` (send a message, creating a new conversation when `conversationId` is null), `POST /{id}/messages/{messageId}/confirm`, `POST /{id}/messages/{messageId}/decline`.
  - **Frontend**: `types/sageChat.ts` + `hooks/useSageChat.ts` (`useSageConversations`, `useSageConversation`, `useSendSageMessage`, `useConfirmSageAction`, `useDeclineSageAction`, all React Query, confirm/decline invalidate the conversation query on success), `components/sage/{SageChatMessage,SageConversationList}.tsx` (message bubbles render pending-action cards with Confirm/Decline buttons while `PENDING`, a plain status line once resolved; `TOOL`-role messages render nothing, they're loop-internal), and `app/(tutor)/sage/page.tsx` — a two-pane layout (conversation list + active thread) with a message composer, wired into the sidebar as "Ask Sage" (`IconMessageChatbot`).
  - **Verified**: backend `./mvnw.cmd compile` clean; frontend `npm run build` (all 19 routes resolve, including `/sage`) and `npm run lint` (clean, only the one pre-existing accepted `lib/api.ts` warning) both pass. Started both the backend (port 8081, since the main checkout's backend was already occupying 8080 with older code) and a matching frontend dev server (port 3001) from this worktree specifically, confirmed `/sage` returns 200 (consistent with every other tutor route, which render nothing server-side behind `useAuthGuard` until client-side auth resolves — not a Sage-specific gap), and drove a real authenticated request straight at the API: registered a tutor, hit `GET /api/sage/chat` with its JWT, got a genuine `200 {"data":[]}` — the list/empty-state path is verified end to end through real Postgres, not just by reading code. **Not verified**: an actual model-backed conversation (send a message, get a tool-use response, confirm/decline a write, see the effect land) — this environment has no reachable `ANTHROPIC_API_KEY` (same constraint that blocked task 6's live curl verification of the tool-use loop), and Kimi WebBridge's browser extension wasn't connected when checked here either, so no click-through was attempted or should be assumed. The confirm/decline mechanics, the tool-use loop, and the write-action execution paths are verified by reading the code against the Anthropic Java SDK's actual types and the DTOs' actual field names, not by an end-to-end run — the same standing limitation every frontend phase in this project has carried since deploy.

- Fixed unauthenticated/expired-JWT requests returning 403 instead of 401. Root cause: `JwtAuthenticationFilter` silently swallows invalid/expired-token exceptions and leaves the request unauthenticated; Spring Security's default `AnonymousAuthenticationFilter` then supplies a placeholder principal, so `.anyRequest().authenticated()` throws `AccessDeniedException` (403) rather than `AuthenticationException` (401). Fixed in `SecurityConfig` by disabling anonymous authentication (`.anonymous(AbstractHttpConfigurer::disable)`) and adding an explicit `HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)`, so any unauthenticated/invalid-token request now correctly returns 401 and the existing frontend handling kicks in. - Fixed a related bug in the login form: a failed login (bad credentials, a real 401 from `/api/auth/login`) was being caught by the same global axios interceptor and triggering a hard `window.location.href` redirect to `/login` before the login page's own error handling could show anything — wiping the form and the error message on every failed attempt.
