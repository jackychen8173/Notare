# Changelog

Notable changes to this project, most recent first. See `CLAUDE.md` for when to add an entry.

## 2026-08-13

- Scaffolded `frontend/` (Next.js 16.3.0 + React 19.2.8, not the spec's Next.js 15 + React 18) and wired up the full design token system, completing build-order phase 8. Deviated from the spec's exact Next.js/React versions since 16 was current stable when this phase started and nothing had been built against 15 yet — no migration cost, unlike the mid-project Spring Boot move. Next.js 16 pulls in Tailwind CSS v4 (CSS-first `@theme` config, replacing the `tailwind.config.js` the spec's era assumed). Used `create-next-app` (App Router, TypeScript, no `src/` dir, `@/*` import alias, matching the spec's flat `app/`/`components/`/`lib/` folder tree exactly) then `shadcn@latest init -d`, which defaulted to Base UI primitives and the `base-nova` style rather than Radix/`new-york` — left as-is since the spec doesn't mandate either. Fonts: Inter + JetBrains Mono via `next/font/google`, both constrained to weights `['400', '500']` per the spec's typography rule, applied as CSS variables on `<html>` (not `<body>`) to sidestep a known shadcn-CLI bug where `@theme inline` self-references `var(--font-sans)` — fixed by using the literal `"Inter", "Inter Fallback"` / `"JetBrains Mono", "JetBrains Mono Fallback"` family-name strings `@theme inline` needs instead of referencing the runtime-injected variable it can't see at build time. `app/globals.css` now encodes the spec's full design system as tokens: the exact hex palette (primary teal, the four sage/AI tokens explicitly commented as never-for-non-AI-content, the five-step neutral scale), a `border-hairline` utility (`border-width: 0.5px`) for the spec's hairline-border rule, base `--radius` set to `0.375rem` (6px) so shadcn's own `rounded-lg` already matches the button radius with no per-component override needed, and an explicit `rounded-card` token (12px) for cards; badges use Tailwind's built-in `rounded-full`. Chart colors (`--chart-1..5`) are extrapolated teal tints, not sage — the spec defines no data-viz palette, and student progress charts aren't AI content, so sage was off the table. `components.json` still says `iconLibrary: "lucide"` (shadcn's default) even though the spec calls for Tabler Icons outline — nothing imports an icon yet, so it's a documented follow-up rather than a fight with unused config. Did **not** install React Query, React Hook Form + Zod, FullCalendar, or Recharts yet — deferred to whichever later phase first uses each, matching the backend's incremental-migrations precedent. Unlike every backend phase so far, this one was actually verified: Node 24.15.0 / npm 11.12.1 are available in this environment, so `npm run build`, `npm run lint`, and a live `npm run dev` request (`curl localhost:3000`) all ran clean, and the compiled CSS was inspected directly (`grep` on the built chunk) to confirm `border-hairline`, `rounded-card`, and the `sage-*` utilities actually generated real rules rather than silently no-op-ing.
- Added SageService and the four Sage endpoints (`sage/`), completing build-order phase 7. Added the Anthropic Java SDK (`com.anthropic:anthropic-java:2.34.0`) to `pom.xml` and an `AnthropicClient` bean (`SageConfig`) built via `AnthropicOkHttpClient.fromEnv()`, reading `ANTHROPIC_API_KEY` directly from the environment (uncommented in `.env.example`, no Spring config binding needed since the SDK resolves it itself). Kept the spec's exact model choice, `claude-sonnet-4-6` — it's still an actively-supported model (not EOL), so the "deviate only with a clear technical reason" precedent from the Spring Boot 3.3→4.1 move doesn't apply here; no reason to substitute a newer model the spec didn't ask for. All four endpoints (`draft-notes`, `review-submission`, `student-progress/{id}`, `pending-reviews`) are tutor-gated and manually triggered — deliberately did not wire an automatic Sage call into `submit_assignment` (phase 6), since "(internal)" in the spec's endpoint list is ambiguous about whether it means auto-triggered-on-submit or just non-UI-facing, and inventing the auto-trigger would mean modifying already-committed phase 6 code with unstated behavior and adding a synchronous external API call to the student-facing submit path. `review-submission` uses the Java SDK's class-based structured-output overload (`.outputConfig(SageFeedback.class)`) so the JSON response is parsed directly into the `SageFeedback` record matching the spec's exact `{correctness, style, suggestions, encouragement}` shape, then serialized via Jackson into `Submission.sageFeedback` (the `@JdbcTypeCode(SqlTypes.JSON)` mapping added in phase 6 is now actually exercised — worth the first real verification once compiled). Went back and changed `SubmissionService.releaseFeedback` (phase 6): `ReleaseFeedbackRequest.tutorFeedback` is no longer required, and the feedback status is now derived — `REVISED` when the tutor adds their own commentary (on top of or instead of Sage's draft), `APPROVED` when they release Sage's draft as-is — with a guard against releasing when there's neither Sage feedback nor tutor commentary to release. Added `SessionRepository.findByTutorIdAndStudentId` and two `SubmissionRepository` derived queries (`findByStudentIdAndAssignment_Course_Tutor_Id`, `countByFeedbackStatusAndAssignment_Course_Tutor_Id`) to support the progress-summary and pending-reviews aggregations. As with every backend phase so far, reviewed by hand — no Maven/JDK available locally, so the SDK's exact type names (`TextBlock`, the structured-output block wrapper) are trusted from current Java SDK examples rather than compiled; used `var` where the structured-output wrapper's return type wasn't confirmable, so a name mismatch there is a compile error rather than a silent bug once actually built.
- Added Assignment and Submission (`assignment/`, `submission/`), completing build-order phase 6 ("no Sage yet"). `AssignmentController` mixes two path prefixes on one controller (`/api/courses/{id}/assignments` for create/list, `/api/assignments/{id}` for get), matching the spec's API layout exactly — a structural deviation from `CourseController`'s single-base-path shape, not a stylistic one. Assignment reads stay tutor-only, same deferral reasoning as Student/Course in phase 4. `submit_assignment` is the first STUDENT-role endpoint in the app (`@PreAuthorize("hasRole('STUDENT')")` at the method level, since `SubmissionController` otherwise needs tutor-only `release_feedback` in the same class) — the student identity comes from the JWT via `Authentication`, never the request body. Added one check beyond the literal spec: `submitAssignment` verifies the student is enrolled in the assignment's course (via `EnrollmentRepository.existsByStudentIdAndCourseId`, already built for phase 4) and returns 403 if not — unlike the tutor-ownership checks elsewhere, this uses 403 rather than 404 since the assignment isn't being hidden, just gated. `release_feedback` only ever sets `feedback_status` to `APPROVED` for now (tutor manually supplies `tutorFeedback` text since there's no Sage draft yet to accept-or-revise) — `REVISED` stays declared in the enum per the spec's data model but is unreachable until Sage exists in phase 7. `Submission.sageFeedback` is mapped with Hibernate's native `@JdbcTypeCode(SqlTypes.JSON)` against a `jsonb` column (available since Hibernate 6.3, no extra dependency) rather than a plain `String` column, to avoid the classic "column is of type jsonb but expression is of type character varying" cast error once something actually writes JSON into it; unverified without a compiler, and the column is null through this entire phase, so worth double-checking when `SageService` starts populating it in phase 7. As with all prior backend phases, reviewed by hand — no Maven/JDK available locally.
- Added Session and SessionNote (`session/`), completing build-order phase 5. `Session` follows the same tutor-ownership pattern as `Course` — `SessionController` is `@PreAuthorize("hasRole('TUTOR')")`, `SessionService` scopes every lookup to the calling tutor via `findByTutorId`/`requireOwnedSession`, and cross-tutor access returns 404 rather than 403 (same reasoning as `CourseService`). `course_id` is nullable per the spec's data model — sessions don't have to be tied to a course — but when one is provided it's validated as both existing and owned by the same tutor, otherwise a session could reference another tutor's course. `SessionNote` is modeled as a `@OneToOne` on `session_id` (unique constraint in `V3__create_sessions.sql`) rather than a one-to-many, since the spec's single `save_session_notes` endpoint (not `add_session_note`) implies one raw-notes blob per session; `SessionService.saveSessionNotes` upserts it (find-by-session-id-or-create) rather than always inserting. `formatted_notes` is left null for now — it's Sage-generated and Sage isn't built until phase 7. Added one piece of business logic beyond the literal spec: `complete_session` rejects completing an already-`CANCELLED` session (409), since the spec defines the status enum but not its transition rules, and completing a cancelled session is a real inconsistency worth catching. As with prior backend phases, reviewed by hand — no Maven/JDK available locally to compile-check.
- Added a "Progress" section to `CLAUDE.md` tracking status against the spec's 13-phase build order, plus a "state a new session should know" note (no frontend yet, no Maven/JDK locally so nothing's been compiled, no real database provisioned so migrations are unverified beyond hand review). Pausing work here for now; next up is Session + SessionNote.

## 2026-08-12

- Added Student, Course, and Enrollment management, all scoped to the owning tutor. There's no separate `Student` entity — students are `User`s with `role=STUDENT`, per the spec's data model — so `student/StudentService` operates on `UserRepository` directly (added `findByRole`). `Enrollment` uses a composite key (`student_id`, `course_id`) via `@EmbeddedId`/`@MapsId` rather than a synthetic UUID id, since the spec's data model conspicuously omits an `id` field for it (unlike every other entity, which lists one first) — a student can only have one enrollment row per course. `V2__create_courses.sql` creates both `courses` and `enrollments`, matching the spec's migration numbering (no separate enrollment migration was listed). All Student/Course/Enrollment endpoints are `@PreAuthorize("hasRole('TUTOR')")`, scoped to courses the calling tutor owns (cross-tutor access returns 404, not 403, to avoid confirming another tutor's course exists) — deliberately not building student-facing read access yet, since the spec doesn't detail that and it would mean inventing unstated authorization rules. `CourseService`'s read methods are `@Transactional(readOnly = true)` so the DTO mappers can safely resolve the lazy `tutor`/`student` associations before the transaction closes (needed since `open-in-view: false` is set). Reviewed by hand as with prior backend changes — no Maven/JDK available locally.
- Preserved the original long-form Notare project spec verbatim at `docs/notare-system-prompt.md`, and added a "Project spec" section to `CLAUDE.md` pointing to it and listing the deliberate deviations made so far (Spring Boot 4.1 instead of 3.3; a few classes added beyond its illustrative folder tree because they're structurally required — see `CLAUDE.md`).
- Built out registration/login end to end: `NotareApplication` (entry point), `common/ApiResponse` + `common/GlobalExceptionHandler`, `auth/dto/{RegisterRequest,LoginRequest,AuthResponse}` (as records), `auth/JwtUtil` (jjwt 0.12.x fluent API), `auth/JwtAuthenticationFilter` (stateless — reads the JWT's email/role claims directly into the `SecurityContext`, no per-request DB lookup), `auth/SecurityConfig` (Spring Security 7 lambda DSL, `/api/auth/**` open, everything else authenticated), `auth/AuthService`, `auth/AuthController`. Added `application.yml` (datasource/JPA/Flyway/JWT config, all via env vars, `ddl-auto: validate` per the spec's "never use `create`" rule) and `.env.example` documenting the required variables. No Maven/JDK available locally, so reviewed by hand rather than compiled; verified the Spring Security 7 DSL and jjwt 0.12.x API shapes against current docs since I couldn't otherwise confirm them.
- Added the `V1__create_users.sql` Flyway migration and the `User` JPA entity (`com.notare.user`), plus `UserRole` (TUTOR/STUDENT) and a `UserRepository` with `findByEmail`/`existsByEmail`. UUID primary keys are generated application-side via `GenerationType.UUID` (JPA 3.1+/Hibernate 6.2+) rather than a DB-side default, so the schema doesn't depend on the `pgcrypto` extension or a specific Postgres version. `role` is stored as `VARCHAR` with a `CHECK` constraint rather than a native Postgres enum, since Flyway-driven schema evolution is easier with `ALTER TABLE` than `ALTER TYPE ADD VALUE`. No Maven/JDK is available in this environment to compile-check, so this was reviewed by hand; the one version-sensitive API used (`GenerationType.UUID`) was confirmed to predate Boot 4 by several versions.
- Added safety harnesses: file deletion and `git push` now always require explicit confirmation, and direct database commands (DB CLIs, mutating Flyway/Liquibase commands) are hard-blocked for Claude entirely. Enforced via `.claude/settings.json` permission rules plus a PreToolUse hook (`.claude/hooks/guard-destructive.js`) that scans full command text so compound/piped commands are caught too, not just literal prefixes. Documented in `CLAUDE.md`.
- Set up `pom.xml` for Spring Boot 4.1.0 / Java 21. Originally scoped for Spring Boot 3.3, but the entire 3.x line reached end-of-life in June 2026 (final release 3.5.16), so moved to the actively-supported 4.x line instead. This changed several artifact names: `spring-boot-starter-web` → `spring-boot-starter-webmvc`, Flyway now needs an explicit `spring-boot-starter-flyway` starter (not just `flyway-core`), and test dependencies are now per-technology (`spring-boot-starter-webmvc-test`, `-data-jpa-test`, `-security-test`) instead of one monolithic `spring-boot-starter-test`.
