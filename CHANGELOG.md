## 2026-08-15

- Started build-order phase 13 (deploy). First step was getting the backend to actually run at all — 6 phases of hand-reviewed Java code had never been compiled, let alone executed. Added a Maven wrapper (`mvnw`/`mvnw.cmd`, `.mvn/wrapper/`) since this machine has JDK 21 (Eclipse Adoptium) but no system Maven; bootstrapped Maven 3.9.9 against it. First real `./mvnw compile` succeeded with zero errors across all 73 classes. Verified the runtime against a disposable Docker `postgres:16` container (remapped to host port 55432 — this machine already runs a native PostgreSQL 17 Windows service on 5432, left untouched) and found two real bugs that no amount of hand-review could have caught:
  1. **Missing `ObjectMapper` bean** — Spring Boot 4.1 rebuilt its Jackson auto-configuration around Jackson 3.x (`tools.jackson.databind.json.JsonMapper`), so it no longer auto-registers a `com.fasterxml.jackson.databind.ObjectMapper` (Jackson 2.x) bean the way Boot 3.x did. `SageService` depends on the Jackson 2.x `ObjectMapper` directly (to serialize `SageFeedback` into the `sageFeedback` jsonb column), so the app failed to start entirely. Fixed by adding an explicit `@Bean ObjectMapper` in `SageConfig`, alongside the existing `AnthropicClient` bean.
  2. **No CORS configuration anywhere in the backend** — never surfaced before because this was the first time the frontend and backend had ever actually talked to each other in a browser. The Next.js dev server (`localhost:3000`) calling the Spring Boot backend (`localhost:8080`) is cross-origin, and with no CORS policy configured, the browser silently blocked every request (login failed with a generic "Something went wrong" — axios's error object has no `.response` for a browser-blocked request, which is what that fallback message is for). Added a `CorsConfigurationSource` bean to `SecurityConfig`, wired into the filter chain via `.cors(...)`, with allowed origins read from a new `CORS_ALLOWED_ORIGINS` env var (defaults to `http://localhost:3000`) — needs to differ between local dev and the eventual Vercel production URL, so it follows the same env-var pattern as `DATABASE_URL`/`JWT_SECRET` rather than being hardcoded.

  After both fixes: full register → login → JWT-protected-endpoint round trip verified against a real Postgres for the first time, and a real browser login through the actual Next.js frontend against the actual Spring Boot backend also confirmed working. Also noted, not yet acted on: `src/test/` has zero test files despite `spring-boot-starter-webmvc-test`/`-data-jpa-test`/`-security-test` all being on the classpath.

- Continued local verification by actually creating data through the app (a real student, then enrolling them in a course) — the phase 11/12 frontend forms had never been exercised against a live backend before. Found and fixed two real bugs in the RHF+Base UI `Select` usages (`components/ui/select.tsx` wraps `@base-ui/react/select`, not Radix, despite following shadcn's Radix-shaped examples):
  1. **Controlled/uncontrolled warning** — both `useForm()` calls driving a `Select` (`EnrollStudentDialog` in `app/(tutor)/courses/[id]/page.tsx`, `ScheduleSessionDialog` in `app/(tutor)/students/[id]/page.tsx`) had no `defaultValues`, so the RHF-controlled field started as `undefined`. Base UI's `Select` only counts as controlled when its value isn't `undefined` on first render, so it started uncontrolled and flipped to controlled the moment a value was picked. Fixed by giving both fields an empty-string default.
  2. **Selected item showing the raw id, not its label** — the deeper issue, and a real API difference from Radix: Base UI's `Select.Value` does not auto-derive its label from the matching `Select.Item`'s rendered children the way Radix's does. Read `resolveValueLabel.mjs` directly (`node_modules/@base-ui/react/internals/`) to confirm — without an `items`/`itemToStringLabel` map on the root or a render-prop `children` function on `Select.Value`, it falls back to stringifying the raw value. Fixed both `SelectValue` usages with the render-prop form (`{(value) => list.find(x => x.id === value)?.name}`) rather than adding a root-level `items` map, since the calling components already have the exact list in scope.

  Both confirmed fixed live in the browser: enrolling a student now shows "Sam Rivera" in the trigger, not the UUID, with no console warning. Worth a broader look later at whether other future `Select` usages need the same render-prop treatment, since nothing in the shadcn-generated component enforces it.
