# Backend Reference

A plain-English guide to what each backend class actually *does*. This is about behavior, not
data shape — for the exact request/response JSON of every endpoint, see the live Swagger UI at
`/swagger-ui.html` (generated by springdoc-openapi, see `CHANGELOG.md`). DTOs (`dto/` records) and
JPA entities are mentioned only briefly here for context.

A pattern that shows up constantly below and is worth naming once: almost every tutor-scoped
lookup (a course, session, assignment, or submission by id) checks that the record actually
belongs to the calling tutor, and if it doesn't, returns **404, not 403**. This is deliberate —
a 403 would confirm to an attacker that a record with that id exists but belongs to someone else;
a 404 reveals nothing. The same trick is used for student enrollment checks on the read side.

---

## `com.notare` (root)

### `NotareApplication`
The entry point (`main`). Nothing else — a bare `@SpringBootApplication` that hands off to Spring
Boot's auto-configuration and component scanning.

## `auth` — registration, login, JWT issuance and verification

### `AuthController`
Two public endpoints, both under `/api/auth`, neither requiring a token: `register` (creates a
new account — this is how a **tutor** account gets created, even though students are normally
created by their tutor via `POST /api/students` instead) and `login`. Both just delegate to
`AuthService` and wrap the result in a `201`/`200` `ApiResponse`.

### `AuthService`
- **`register`** — rejects a duplicate email with `409 Conflict`, otherwise hashes the password
  (via the injected `PasswordEncoder`), saves a new `User` with whatever role the request asked
  for (`TUTOR` or `STUDENT`), and returns a signed JWT for it.
- **`login`** — looks up the user by email, and if either the email doesn't exist or the password
  doesn't match the stored bcrypt hash, returns a generic `401 Unauthorized` ("Invalid email or
  password") — deliberately the *same* message either way, so a failed login never reveals whether
  the email was even registered.
- **`toAuthResponse`** (private) — the shared step that actually mints the JWT (via `JwtUtil`) and
  builds the `AuthResponse` body both public methods return.

### `JwtUtil`
Owns all JWT creation/verification. The secret key and expiration are read from config
(`jwt.secret`, `jwt.expiration-ms`).
- **`generateToken`** — builds a signed JWT whose subject is the user's email and which carries
  two custom claims: `userId` and `role`. The role claim is what makes role-based authorization
  possible without a database hit on every request.
- **`parseClaims`** — verifies the signature and decodes the claims; throws if the token is
  malformed, expired, or signed with a different key.
- **`extractEmail`** / **`extractRole`** — pull the subject / `role` claim out of a token.
- **`isValid`** — `true` if `parseClaims` doesn't throw, `false` otherwise. Used by the filter to
  decide whether to trust a token at all before reading anything out of it.

### `JwtAuthenticationFilter`
A servlet filter that runs once per request, before Spring Security's normal authentication
machinery. If the request has an `Authorization: Bearer <token>` header and the token is valid, it
builds a Spring Security `Authentication` (email as principal, `ROLE_<role>` as the single granted
authority) and puts it in the `SecurityContext` — this is what makes `@PreAuthorize("hasRole(...)")`
and `Authentication.getName()` work everywhere else in the app. Critically, it does **not** hit the
database to double check the user still exists — the whole point of a stateless JWT is that
everything needed to authenticate the request is inside the token itself. If the token is present
but invalid, it clears the security context and lets the request continue *unauthenticated* (the
downstream `authorizeHttpRequests` rule is what actually rejects it with a 401/403 later).

### `SecurityConfig`
Wires together all of the above into the actual security policy:
- Disables CSRF (irrelevant for a stateless, header-token API) and sets the session policy to
  `STATELESS` (Spring Security won't create or read `HttpSession`s — the JWT is the only session
  state that exists).
- Declares which paths need no authentication at all: `/api/auth/**` (registration/login, which by
  definition can't require a token) and the Swagger UI / OpenAPI JSON paths. Everything else
  requires a valid, authenticated request.
- Registers `JwtAuthenticationFilter` to run before Spring's built-in username/password filter.
- **`corsConfigurationSource`** — builds the CORS policy from the `cors.allowed-origins` env var
  (comma-separated), allowing the standard HTTP methods and any header. This exists specifically
  because the browser blocks cross-origin requests from the Next.js frontend to this API without
  it — see the CORS bug written up in `CHANGELOG.md` (2026-08-15).
- **`passwordEncoder`** — the app-wide `BCryptPasswordEncoder` bean, used by `AuthService` and
  `StudentService` to hash passwords before they ever touch the database.

## `user` — the shared account model

There's no separate `Student` entity — a student is just a `User` with `role = STUDENT`. This is
why `StudentService` (below) operates directly on `UserRepository` rather than having its own
repository.

### `User` (entity)
Fields: `id`, `name`, `email` (unique), `password` (bcrypt hash, never returned in any response
DTO), `role`, `createdAt` (auto-set on insert via `@PrePersist`).

### `UserRepository`
Standard CRUD plus three derived-query methods: `findByEmail` (used everywhere auth needs to
resolve "who is making this request"), `existsByEmail` (duplicate-registration check), and
`findByRole` (how `StudentService.listStudents` finds every student regardless of which tutor
"owns" them — see below, students aren't actually tutor-scoped by the schema itself).

## `student` — tutor-facing student management

### `StudentController`
Class-level `@PreAuthorize("hasRole('TUTOR')")` — every endpoint here is tutor-only. `POST` to
create a student account, `GET` to list all students or fetch one by id, `PUT` to rename/re-email
one.

### `StudentService`
- **`createStudent`** — same duplicate-email check and password-hashing as `AuthService.register`,
  but hardcodes `role = STUDENT` regardless of what's in the request (there's no way to create a
  tutor through this path).
- **`listStudents`** — returns *every* student in the system, not scoped to "students this tutor
  has taught." Worth knowing: nothing in the data model actually ties a student to a specific
  tutor directly — that relationship only exists indirectly, through course enrollments and
  sessions.
- **`getStudent`** — 404s if the id doesn't belong to a user with `role = STUDENT` (so a tutor
  can't fetch another tutor's account through this endpoint by guessing an id).
- **`updateStudent`** — updates name/email; if the new email collides with a *different* existing
  account, 409s.
- **`requireStudent`** (private) — the shared "look up by id and make sure it's actually a
  student" helper all three read/write methods above funnel through.

## `course` — courses, and the enrollment relationship between students and courses

### `Course` (entity)
Fields: `id`, `tutor` (owning `User`), `name`, `subject`, `description`.

### `Enrollment` / `EnrollmentId` (entity + composite key)
The join between a student and a course. Deliberately uses a composite primary key
(`student_id` + `course_id`, via `EnrollmentId`) rather than its own synthetic id — the schema
treats "this student is enrolled in this course" as the fact being recorded, not a first-class
object with its own identity, and the composite key means a student physically can't have two
enrollment rows for the same course.

### `CourseController`
Class-level tutor-only. Create a course, list the calling tutor's own courses, fetch one by id,
enroll a student into one, list who's enrolled.

### `CourseService`
This class does double duty — it backs both the tutor-facing `CourseController` and the
student-facing `StudentCourseController` below, which is why it has two parallel sets of methods
(`list/getCourse` for tutors vs. `list/getEnrolledCourse` for students).
- **`createCourse`** — attaches the course to whichever tutor's email is on the request.
- **`listCourses`** / **`getCourse`** — tutor-scoped; `getCourse` funnels through
  `requireOwnedCourse`, so fetching another tutor's course id 404s.
- **`enrollStudent`** — verifies the course belongs to the calling tutor, the target user exists
  and is actually a student, and that they aren't already enrolled (409 if so), before inserting
  the `Enrollment` row.
- **`listEnrolledCourses`** / **`getEnrolledCourse`** — the student-facing equivalents, scoped by
  the enrollment table rather than by ownership. `getEnrolledCourse` 404s (not 403) if the course
  exists but the calling student isn't enrolled in it, same "don't confirm existence" reasoning as
  the tutor-ownership checks.
- **`listEnrolledStudents`** — the roster for a course, tutor-only, tutor-ownership-checked first.
- **`requireOwnedCourse`** / **`requireEnrolledCourse`** (private) — the two shared gate-keeping
  helpers everything above funnels through.

### `StudentCourseController`
Class-level `@PreAuthorize("hasRole('STUDENT')")`, under `/api/student/courses`. Two read-only
endpoints (list my enrolled courses, get one of them by id) — both self-scoped from the JWT, with
no `studentId` parameter anywhere in the request. This whole controller (and its three siblings
under `assignment`/`session`/`submission`) didn't exist until very late in the project; see
`CLAUDE.md`'s "Project spec" section for why the student-facing read API was deferred three times
before finally being built.

### `CourseRepository` / `EnrollmentRepository`
`CourseRepository` adds one derived query, `findByTutorId`. `EnrollmentRepository` adds
`findByCourseId`, `findByStudentId`, and `existsByStudentIdAndCourseId` — that last one is the
single most-reused method in the whole backend; it's the actual mechanism behind every
"is this student enrolled" check across courses, assignments, and submissions.

## `session` — tutoring sessions and the notes taken during them

### `Session` (entity)
Fields: `id`, `tutor`, `student`, `course` (nullable — a session doesn't have to be tied to a
specific course), `date`, `subject`, `duration`, `status` (`SessionStatus`).

### `SessionNote` (entity)
One-to-one with `Session` (enforced by a unique constraint on `session_id`, not a
one-to-many) — a session has at most one notes record, which gets *overwritten* on each save
rather than accumulating a history. Holds `rawNotes` (what the tutor actually typed) and
`formattedNotes` (Sage's polished rewrite, null until Sage has been asked to draft it).

### `SessionStatus` (enum)
`SCHEDULED` → `COMPLETED` or `CANCELLED`. `COMPLETED` and `CANCELLED` are both terminal; see
`completeSession` below for the one transition rule that's actually enforced.

### `SessionController`
Class-level tutor-only. Create/list/get sessions, mark one complete, and get/save its notes.

### `SessionService`
- **`createSession`** — student must exist and actually be a student; if a `courseId` is given, it
  must exist *and* belong to the same tutor (404 otherwise) — a session can't reference another
  tutor's course. New sessions always start `SCHEDULED`.
- **`listSessions`** / **`getSession`** — tutor-scoped, same ownership-check pattern as everywhere
  else.
- **`listSessionsForStudent`** — the student-facing read (used by `StudentSessionController`
  below): every session for the calling student, regardless of which tutor ran it.
- **`completeSession`** — the one business rule beyond the literal data model: refuses (`409`) to
  mark an already-`CANCELLED` session as `COMPLETED`. Nothing stops completing a session that's
  already `COMPLETED` (that's just a no-op re-save), but cancelled-then-completed is treated as a
  real inconsistency worth blocking.
- **`getSessionNotes`** — returns `null` (not a 404) when no notes have been saved yet; "no notes
  yet" isn't an error condition, it's just the normal state of a freshly scheduled session.
- **`saveSessionNotes`** — an upsert: finds the session's existing `SessionNote` or creates a new
  one, then overwrites `rawNotes`. This is why there's no "add a note" endpoint, only "save the
  notes" — there's exactly one raw-notes blob per session, not a running log.

### `StudentSessionController`
Student-only, one endpoint: list the calling student's own sessions across every tutor/course.

### `SessionRepository` / `SessionNoteRepository`
`SessionRepository` adds `findByTutorId`, `findByTutorIdAndStudentId` (used by Sage's progress
summary to pull one student's session history), and `findByStudentId` (the student-facing read).
`SessionNoteRepository` adds `findBySessionId`, the lookup behind the one-note-per-session upsert.

## `assignment` — homework assignments attached to a course

### `Assignment` (entity)
Fields: `id`, `course`, `title`, `description`, `dueDate`.

### `AssignmentController`
Tutor-only. Note the URL shape is deliberately asymmetric: creating/listing assignments is nested
under `/api/courses/{courseId}/assignments`, but fetching a single assignment is
`/api/assignments/{id}` (no course id needed, since the assignment id alone is already unique).

### `AssignmentService`
- **`createAssignment`** / **`listAssignments`** / **`getAssignment`** — tutor-scoped through the
  owning course, same 404-not-403 ownership pattern (an assignment is "owned" by whichever tutor
  owns its course).
- **`listAssignmentsForEnrolledCourse`** / **`getAssignmentForStudent`** — the student-facing
  reads. Both check *enrollment*, not ownership: a course/assignment that exists but the student
  isn't enrolled in still 404s, never revealing that it exists.
- The four `require*` private helpers mirror the same split everywhere else in the codebase: two
  for "does this tutor own it" (`requireOwnedCourse`, `requireOwnedAssignment`), two for "is this
  student enrolled in it" (`requireEnrolledCourseForAssignments`, `requireEnrolledAssignment`).

### `StudentAssignmentController`
Student-only, under `/api/student/*`: list an enrolled course's assignments, get one assignment by
id. Both self-scoped from the JWT.

### `AssignmentRepository`
One derived query, `findByCourseId`.

## `submission` — a student's homework submission, and the feedback release workflow

This is the package with the most actual business logic in the app, because it's where Sage
feedback has to stay hidden from students until a tutor explicitly approves it.

### `Submission` (entity)
Fields: `id`, `assignment`, `student`, `content` (the submitted code/text), `sageFeedback` (raw
JSON string — Sage's structured `{correctness, style, suggestions, encouragement}` output, stored
via Hibernate's native JSON column type rather than a plain string column), `tutorFeedback`,
`feedbackStatus` (`FeedbackStatus`), `grade`, `submittedAt`, `releasedAt` (null until a tutor
releases feedback).

### `FeedbackStatus` (enum)
`PENDING` (submitted, nothing released yet) → `APPROVED` (tutor released Sage's draft as-is) or
`REVISED` (tutor added their own commentary on top of, or instead of, Sage's draft). Which of the
two you land on is *derived*, not chosen explicitly — see `releaseFeedback` below.

### `SubmissionController`
Mixed authorization at the method level (there's no single class-level role, unlike most other
controllers): `submitAssignment` is student-only, everything else (`getSubmission`,
`listSubmissionsForAssignment`, `releaseFeedback`) is tutor-only.

### `SubmissionService`
- **`submitAssignment`** — the first student-role write path in the whole app. Explicitly checks
  the student is enrolled in the assignment's course (`403`, not `404`, since this is a student
  acting on their own behalf, not a tutor probing for another tutor's data — there's nothing to
  hide here). New submissions always start `PENDING`.
- **`getMySubmission`** — the student-facing status check: same enrollment check, then returns the
  *most recent* submission for that assignment (via
  `findFirstByStudentIdAndAssignmentIdOrderBySubmittedAtDesc` — nothing stops a student submitting
  more than once, and the latest one is what matters), rendered through **`SubmissionResponse.forStudent`**
  rather than the tutor-facing `from`. This is the actual mechanical enforcement of "Sage feedback is
  never shown to students without tutor approval": `forStudent` nulls out `sageFeedback`,
  `tutorFeedback`, and `grade` whenever `releasedAt` is unset, so the gate lives in the DTO itself
  rather than depending on every future caller remembering to check a flag.
- **`getSubmission`** / **`listSubmissionsForAssignment`** — tutor-facing reads, ownership-checked
  through the submission's assignment's course's tutor (yes, three hops).
- **`releaseFeedback`** — the workflow's core method. Refuses to release (`409`) if there's neither
  Sage feedback generated yet nor tutor commentary supplied — nothing to actually show the student.
  If the tutor supplied their own `tutorFeedback` text, the status becomes `REVISED`; if they
  released Sage's draft with no added commentary, it becomes `APPROVED`. Either way this stamps
  `releasedAt`, which is the timestamp `forStudent` checks to decide whether to reveal anything.

### `StudentSubmissionController`
Student-only, one endpoint: `GET /api/student/assignments/{id}/submission`, delegating straight to
`getMySubmission`.

### `SubmissionRepository`
Four derived queries: `findByStudentIdAndAssignment_Course_Tutor_Id` (a student's submission
history scoped to one tutor — used by Sage's progress summary), `findByAssignmentId` (the
tutor-facing submission list for one assignment), `countByFeedbackStatusAndAssignment_Course_Tutor_Id`
(how the pending-reviews badge counts `PENDING` submissions across a tutor's whole roster without
loading them), and `findFirstByStudentIdAndAssignmentIdOrderBySubmittedAtDesc` (the "most recent
submission" lookup behind `getMySubmission`).

## `sage` — the AI layer (all Claude API calls go through here, and only here)

### `SageController`
Tutor-only, four endpoints, all manually triggered from the UI — nothing elsewhere in the app
calls Sage automatically (e.g. submitting an assignment does *not* auto-trigger a review; a tutor
has to explicitly ask for one). `draft-notes`, `review-submission`, `student-progress/{id}`,
`pending-reviews`.

### `SageService`
The single point of contact with the Anthropic API — no controller or other service calls
`AnthropicClient` directly.
- **`draftSessionNotes`** — requires raw notes to already exist for the session (404s with an
  explicit "save notes first" message otherwise), sends them to Claude with a prompt instructing
  it to preserve all factual content and never invent details, and overwrites `formattedNotes`
  with the result.
- **`reviewSubmission`** — sends the submission's raw content to Claude using the SDK's
  *structured-output* mode (`outputConfig(SageFeedback.class)`), so the response is parsed
  directly into the `{correctness, style, suggestions, encouragement}` shape rather than freeform
  text, then serialized to JSON and stored on `Submission.sageFeedback`. This is a *draft* only —
  nothing here makes it visible to the student; that only happens later, through
  `SubmissionService.releaseFeedback`.
- **`generateProgressSummary`** — pulls a student's full session and submission history for the
  calling tutor specifically (not across all tutors), 404s if there's no history at all to
  summarize, and asks Claude for a short 2–4 sentence summary. `buildProgressPrompt` (private) is
  what actually formats that history into a plain-text prompt.
- **`pendingReviewsCount`** — a cheap count (not a list) of how many of the tutor's submissions are
  still sitting at `FeedbackStatus.PENDING` — what a "you have N submissions to review" badge would
  read from.
- **`complete`** / **`completeStructured`** (private) — the two low-level wrappers around the
  actual Claude API call: one for plain-text completions (notes, progress summaries), one for
  structured JSON output (feedback). Both hardcode the model to `claude-sonnet-4-6`, matching the
  spec's exact choice.
- **`toJson`** (private) — serializes a `SageFeedback` record to a JSON string via the injected
  `ObjectMapper`, for storage in the `sageFeedback` column.

### `SageConfig`
Two beans: `anthropicClient` (built via `AnthropicOkHttpClient.fromEnv()`, which reads
`ANTHROPIC_API_KEY` straight from the environment — no Spring config binding involved), and
`objectMapper`. That second one exists only because of a real bug found while getting the backend
running for the first time: Spring Boot 4.1's own Jackson auto-configuration builds a Jackson 3.x
mapper, not the classic Jackson 2.x `ObjectMapper` this service's constructor asks for, so without
this explicit bean the whole application fails to start. See `CHANGELOG.md` (2026-08-15) for the
full story.

### `SageFeedback` (record)
The exact shape of one piece of AI-generated homework feedback: `correctness`, `style`,
`suggestions`, `encouragement` — all plain strings, matching the spec's Sage feedback format
verbatim.

## `common` — cross-cutting concerns shared by every feature package

### `ApiResponse<T>`
The envelope every single endpoint response is wrapped in: `{success, message, data}`. Three
factory methods (`success(data)`, `success(message, data)`, `error(message)`) — there's no public
constructor, so a response can only be built through one of these three known shapes.

### `GlobalExceptionHandler`
Catches exceptions thrown anywhere in the app and turns them into the same `ApiResponse` envelope
instead of a raw stack trace or Spring's default error page:
- **`ResponseStatusException`** → whatever status code the exception was thrown with, message from
  its `reason`. This is the exception type virtually every service method above throws for 404s,
  409s, 401s, etc. — this handler is what actually turns `new ResponseStatusException(NOT_FOUND, "...")`
  into a real HTTP response.
- **`MethodArgumentNotValidException`** → `400 Bad Request`, with the *first* validation failure
  message (e.g. a `@NotBlank` or `@Email` violation on a request DTO).
- Anything else uncaught → `500`, with a deliberately generic "An unexpected error occurred"
  message rather than leaking internal exception details to the client.

### `OpenApiConfig`
Pure configuration, no logic: names the API ("Notare API") for Swagger UI, and registers a
`bearerAuth` HTTP/JWT security scheme so Swagger's "Authorize" button knows how to attach a token
to test requests. Added alongside springdoc-openapi — see `CHANGELOG.md` (2026-08-15).
