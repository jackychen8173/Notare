# Notare — Working Rules

## Project spec

The full original project spec (tech stack, data model, API design, Sage feedback format, design system, folder structure, role-switching commands, coding standards, build order) lives in `docs/notare-system-prompt.md`, kept verbatim as originally written. Known deviations from it, made deliberately as the project progressed:

- **Spring Boot 4.1 / Java 21, not Spring Boot 3.3** — the entire 3.x line reached end-of-life in June 2026, see `CHANGELOG.md`. This changed some artifact/package names (`spring-boot-starter-webmvc`, explicit `spring-boot-starter-flyway`, per-technology test starters).
- A few classes exist beyond the spec's illustrative folder tree because they're structurally required, not optional: `NotareApplication.java` (entry point), `auth/JwtAuthenticationFilter.java` (JWT can't protect endpoints without a filter), and an `auth/dto/` subpackage for request/response DTOs (the spec's "DTOs for all request/response objects" rule needs somewhere to live).
- **Next.js 16 / React 19, not Next.js 15 / React 18** — 16 was the current stable major when phase 8 started (`npm view next version` → `16.3.0`; Next 16 requires React 19), and nothing had been built against 15 yet, so there was no migration cost to starting fresh on current. Brings Tailwind CSS v4 (CSS-first `@theme` config, not the `tailwind.config.js` the spec's era assumed) and the `middleware.ts` → `proxy.ts` rename (not yet relevant — no middleware/proxy exists yet).
- **shadcn/ui CLI defaults differ from its own docs** — `shadcn init -d` on the installed CLI version produced `--base base-ui` (Base UI primitives) and `style: "base-nova"`, not the Radix/`new-york` combination shown in most shadcn examples. Left as the CLI's actual current default rather than forcing Radix/new-york, since nothing in the spec requires either specifically.
- **Icon library: Tabler Icons (outline), not shadcn's default Lucide** — the spec's design system explicitly calls for Tabler. `components.json` still says `"iconLibrary": "lucide"` (shadcn's default, unedited) since no component has imported an icon yet; swap to `@tabler/icons-react` directly whenever the first icon is actually needed rather than fighting shadcn's icon-swapping machinery for an unused setting.
- **Student routes live under `student/` (a real segment), not `(student)/` (a route group)** — the spec's frontend tree gives `(tutor)/` and `(student)/` identical page paths (`dashboard`, `courses`, `courses/[id]`, `assignments/[id]`), which is actually invalid in Next.js: route groups don't add a URL segment, so both groups would try to serve the same route. Asked the user; resolved as tutor keeping the bare paths (`/dashboard`, `/courses`, ...) as the primary experience, student screens moving to `/student/dashboard`, `/student/courses`, etc.
- **A whole student-facing read API exists that the spec never described** — `course/StudentCourseController.java`, `assignment/StudentAssignmentController.java`, `session/StudentSessionController.java`, `submission/StudentSubmissionController.java`, all under `/api/student/*`, self-scoped from the JWT (no `studentId` params anywhere). The spec's build order deferred student-facing reads three times over (phases 4, 6, 7) with the same "would mean inventing unstated authorization rules" reasoning each time; phase 12 is where that became unavoidable, since building student screens with genuinely zero student read access wasn't possible. Asked the user before building it, given the scale (a new authorization/scoping model from scratch, not just filling a gap symmetric with an existing endpoint). See `CHANGELOG.md` for the exact endpoint list and the `SubmissionResponse.forStudent()` release-gating logic.

## Quiz / Assessment feature (post-launch, complete)

Added after the admin portal, as its own scoped-then-planned addition rather than a phase-list entry, same reasoning as the admin portal and CI/CD being tracked separately. Tutors author MC/TF/short-answer/essay questions under a course (`V16__create_quizzes.sql`: `quizzes`, `quiz_questions`, `quiz_question_options`, `quiz_attempts`, `quiz_answers`); students get a single, optionally-timed attempt with a hard auto-submit at the deadline (client countdown triggers it, but a server-side `finalizeIfExpired` check on every attempt-touching service method is the actual authority — no scheduled job). MC/TF auto-grade instantly; short-answer/essay go to the tutor, optionally with a Sage-drafted suggested score/feedback (`draft_quiz_answer_feedback`/`release_quiz_attempt`, two new chat tools) that's never shown to the student until the tutor releases the attempt — same `releasedAt`-gated trust boundary as `Submission`. New backend packages `com.notare.quiz` (content, mirrors `assignment/`) and `com.notare.quizattempt` (attempts/answers, mirrors `submission/`); new frontend surface: a tutor quiz builder + grading page reached by ID from a course's detail page (no top-level list route, same pattern as assignments), a student quiz overview page, and a **new top-level route outside `app/student/`**, `app/quiz-take/[attemptId]/`, with its own minimal chrome-free layout — a timed attempt can't have a sidebar/nav to click away through, and `app/student/layout.tsx`'s persistent chrome can't be opted out of from a nested page. See `CHANGELOG.md` 2026-09-23 for the full file list and design-decision writeup (single-attempt enforced via a DB unique constraint, MC is single-correct/radio in v1 not multi-select, TRUE_FALSE reuses the option table via two synthesized rows). Same standing limitation as every phase since deploy: verified via backend compile, frontend build/lint, and a live dev-server smoke test, but never exercised against a live backend+database in this environment (no reachable Postgres/`ANTHROPIC_API_KEY` here). Not yet deployed to production.

## Coding-environment assignments (post-launch, complete)

A real Java code editor (CodeMirror 6) plus a "Run" button on assignment submissions, for AP CSA classes. Scoped with the user first: editor + Run only (auto-graded test cases is a natural future extension, not built); execution via a self-hosted sandbox — landed on **Vercel Sandbox** (Firecracker microVMs) after confirming Railway (the backend's host) has no Docker-in-Docker support, so a literal self-hosted-Docker approach was never actually available. Cross-checked against CSAwesome2 (Runestone's AP CSA platform), which does the equivalent the same way: a sandboxed backend server, not in-browser — and its constraints (filename matches the public class name, ~25s compile+run cap) match what's built here.

The Spring Boot backend (Railway) has no Vercel OIDC, so it can't call the Sandbox SDK directly — the fix is **one deliberately thin Next.js route**, `frontend/app/api/code-run/route.ts`, gated only by a shared secret (`CODE_RUN_INTERNAL_SECRET`), doing zero authentication/authorization itself. The Spring backend (new `com.notare.coderun` package, mirrors `assignment/`'s ownership pattern) remains the sole public API surface and sole authorization owner, calling that route server-to-server. **This is the first backend logic ever placed in the Next.js app** — everything before this was 100% in the Spring service; worth knowing if a similar "which side should this logic live on" question comes up again. A one-time live setup (`frontend/scripts/setup-java-sandbox.mjs`, re-runnable to bump the JDK version) bakes a JDK into a snapshot (`JAVA_SANDBOX_SNAPSHOT_ID`) so every real "Run" boots fast from it instead of installing a JDK per request.

v1 limitations, deliberate not accidental: no stdin/`Scanner` input, no AWT/Swing/graphics, exactly one `public class` per submission (parsed via regex, not a real parser). See `CHANGELOG.md` 2026-09-23 (2) for the full write-up, including a real bug found during live testing (the minimal `vercel/sandbox/ubuntu` base image doesn't pre-create `/vercel/sandbox` as a directory — fixed by explicitly `mkdir -p`-ing a working directory rather than assuming that path exists).

**This is also the first feature in this project's history verified against a real, live execution path** — not just backend-compiles / frontend-builds-and-lints (though those passed too), but an actual `npm run dev` hitting the real deployed Vercel Sandbox infrastructure with real Java source, covering success, compile error, runtime exception, and both rejection paths. Vercel Sandbox execution needs no local Postgres, so this sidesteps the standing "can't run the backend end-to-end here" limitation that's applied to every feature since deploy.

**Live setup already done for real** (not just planned): the JDK snapshot exists; `JAVA_SANDBOX_SNAPSHOT_ID`/`CODE_RUN_INTERNAL_SECRET` are set on Vercel (production + development); `CODE_RUN_SERVICE_URL`/`CODE_RUN_INTERNAL_SECRET` are set on Railway's `backend` service (set with `--skip-deploys`, so this did not trigger a deploy of the old code). **Not done**: nothing is deployed to production yet — a live test through the actual deployed frontend→backend→sandbox chain (as opposed to local dev → live sandbox, which *is* verified) is still pending a real deploy.

## Safety harnesses (always enforced, in every permission mode including auto mode)

1. **No file deletion without confirmation.** `rm`, `git rm`, `git clean`, `Remove-Item`, `rmdir`, `del`, and similar always require an explicit confirmation prompt.
2. **Every `git push` requires explicit confirmation.** Same enforcement, no exceptions.
3. **Database changes are done by a human, never by Claude.** Direct DB CLIs (`psql`, `mysql`, `mongosh`, `sqlcmd`, `sqlite3`, `redis-cli`) and mutating Flyway/Liquibase commands (`migrate`, `clean`, `repair`, `undo`, `baseline`, `update`, `rollback`, `dropAll`) are hard-blocked outright — Claude cannot run them at all, confirmation or not. Claude may still author migration SQL files (e.g. `V1__create_users.sql`) for the user to review and apply themselves; read-only inspection commands like `flyway:validate`/`flyway:info` are not blocked.
   - Caveat: starting the app locally (`mvn spring-boot:run`) still triggers Flyway's normal auto-migration against whatever database it's configured against — that's Spring Boot's own startup behavior, not a command Claude runs directly, so this harness doesn't catch it. Point local dev at a disposable/local database if you want to avoid that too.

Enforced by `.claude/settings.json` (`permissions.deny`/`permissions.ask`, plus `autoMode.hard_deny` for the built-in auto-mode classifier) and the `.claude/hooks/guard-destructive.js` PreToolUse hook, which scans full command text so compound commands (`docker exec db psql ...`, `build && git push`) are still caught, not just literal prefixes. These three rules hold in every permission mode — default, auto, accept-edits — because they're enforced mechanically, not left to in-the-moment judgment.

## Auto mode

Toggle Claude Code's built-in "auto" permission mode (`/config` → permission mode, or Shift+Tab to cycle) to let Claude run routine local dev work — builds, tests, lint, `git status`/`diff`/`log`/`add`/`commit`, file edits — without a prompt each time. The three rules above still apply in every mode, including auto.
